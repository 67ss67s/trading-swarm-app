# OKX Agent Trade Kit 适配(OKX Dev Day 参赛版)— 设计与契约

日期:2026-09-20。仓库:`<repo>`(从 trade-gate 主仓 fork,分支 `okx-devday`)。
目标:保留交易核心(策略/线程/闸门/风控/复盘/楼层),把交易所从 Binance 换成 OKX,通过官方
**Agent Trade Kit(ATK)** 打通行情、账户、下单、保护单、撤单、成交对账。

## 0. 结论先行

- **执行通道 = 代码直接调用 `okx` CLI(`@okx_ai/okx-trade-cli`,`--json`)**,不经过模型。
  理由:ATK 的 CLI 本地签名、密钥只在 `~/.okx/config.toml`、退出码 0/1 明确、`--json` 原样输出
  OKX v5 的 data 数组;和主仓「账户/结算查询移出模型」的方向一致。这条通道的 `kind` 叫 `okx`。
- **MCP(`@okx_ai/okx-trade-mcp`)保留为对话侧可选**:给聊天/角色 agent 的 CLI(claude/codex)
  挂 OKX MCP 做「问答式」查询;不做交易执行通道。本轮不接线,只在执行页给出 `okx setup --client claude-code`
  的说明(后续再做)。
- **行情 = 直接打 OKX 公共 REST v5**(不需要 key,不走 CLI 进程,K 线抓得频繁)。
- **内部币种口径不变**:全系统仍用 `BTCUSDT` 这种规范符号(策略库、线程、DB、前端都不改);
  OKX 侧的 `instId`(`BTC-USDT-SWAP`)和合约张数只在 OKX 适配层里换算。
- **Binance 不删代码,按交易所开关隐藏**:`TG_EXCHANGE=okx|binance`,fork 默认 `okx`。
  `okx` 模式下 demo/cli/agent_mcp/mcp 四个 Binance 通道不注册、UI 不显示,Binance OAuth 路由不挂。
  paper 通道保留(行情来源随交易所)。

## 1. 环境与配置

- 安装:`npm i -g @okx_ai/okx-trade-cli`(本机装在 `~/.local/bin/okx`,1.4.7)。
  网关找二进制的顺序:`TG_OKX_CLI` → `~/.local/bin/okx` → PATH 上的 `okx`。
- 凭证:`okx config init` 交互生成 `~/.okx/config.toml`;profile 里 `demo = true` 即模拟盘。
  网关只传 `--profile <name>`(`TG_OKX_PROFILE`,默认 `default_profile`),**永远不读 key**,
  **也不打开那个文件**:profile 名与 demo 标志跑一次 `okx config show`(**不加 `--json`**)解析 ——
  掩码版只印 `default_profile` / `[profile]` / `api_key: ****xxxx` / `demo`,secret 与 passphrase 根本不印;
  `--json` 那一份是**未掩码**的全量配置,禁止使用。CLI 把配置路径写死在 `~/.okx/config.toml`,
  没有开关能改,所以网关侧不提供配置路径覆盖(曾经的 `TG_OKX_CONFIG` 已删:它只会让检查与执行分叉)。
- 模拟/实盘:**除非显式 `TG_OKX_LIVE=1` 且 profile 自己 `demo=false`,每条 CLI 命令都强制带 `--demo`**
  (全局开关,与 `--live` 互斥)。`--profile` 只选名字,同名 profile 在别处可以是实盘,光靠启动检查约束不了执行环境。
  网关按 profile 的 `demo` 字段判定,并在 `/api/execution` 里回显 `okx.demo: boolean`;
  开发期一律模拟盘。实盘 = profile `demo=false` 且启动时显式 `TG_OKX_LIVE=1`,否则网关拒绝启动该通道
  (双保险,避免 dev 实例误连实盘)。
- 网络:本机有 Clash 代理(`HTTPS_PROXY=http://127.0.0.1:7897`),CLI 自己读环境变量,不用额外处理;
  公共 REST 用 Node `fetch`,同样走环境代理。

## 2. 符号与数量换算(`packages/gateway/src/demo/okx/instruments.ts`)

| 内部 | OKX |
|---|---|
| `BTCUSDT` | `instId = BTC-USDT-SWAP` |
| qty(币的数量,如 `0.013` BTC) | `sz`(合约张数)= qty / ctVal,向下取整到 `lotSz` |
| `SymbolRules.step_size` | `ctVal × lotSz`(币) |
| `SymbolRules.min_qty` | `ctVal × minSz` |
| `SymbolRules.tick_size` | `tickSz` |
| `SymbolRules.min_notional` | `ctVal × minSz × 最新价`(OKX 没有独立最小名义;用它做保守下限) |
| `SymbolInfo.status` | `state === 'live'` → `TRADING`,否则原样 |
| `SymbolInfo.price_precision / qty_precision` | 由 tickSz / step_size 小数位数推 |

只收录 `instType=SWAP`、`ctType=linear`、`settleCcy=USDT`、`state=live` 的合约。
规范符号 = `instFamily` 去掉 `-`(`BTC-USDT` → `BTCUSDT`);反向映射用缓存表,查不到就按
`<BASE>USDT` 规则拼(BASE = 去掉尾部 `USDT`)。instruments 缓存 10 分钟。

成交/持仓里的张数一律换回币的数量再交给 runtime(`PositionView.qty`、`SettlementTrade.qty`、
`OrderStatusView.executed_qty`、`OpenOrderView.qty`)。

## 4. 执行通道 `OkxCliBackend`(`packages/gateway/src/demo/execution-okx.ts`,`kind: 'okx'`)

以 `execution-cli.ts`(Binance CliBackend)为模板:spawn + JSON 解析 + 错误分类
(`transport | rejected | local_reject`,写操作超时 = ambiguous → `unknown`)。所有命令统一前缀
`okx --json --profile <p>`;写命令超时 20s,读 15s。

| ExecBackend 方法 | okx CLI | 换算/语义 |
|---|---|---|
| start() | `account config`(读 `posMode`、`acctLv`)+ `market instruments --instType SWAP` | `posMode` 必须是 `net_mode`;是 `long_short_mode` 就报错提示用 `okx account set-position-mode --posMode net_mode`(不自动改账户设置) |
| account() | `account balance` + `account positions --instType SWAP` + `swap orders --json`(open)+ `swap algo orders --ordType conditional --json` + `swap algo orders --ordType oco --json` | equity=`totalEq`(USDT 详情用 `details[ccy=USDT].eq` 更准,取 USDT 的 `eq`),available=`details[USDT].availBal`,unrealized=`details[USDT].upl`;持仓 side 由 `pos` 正负(net 模式)决定,qty=`|pos|×ctVal`,entry=`avgPx`,mark=`markPx`,upl=`upl`,leverage=`lever`;挂单 type/side 翻成**内部词表**(Binance 口径):普通单 `ordType`/`side` 直接大写;算法单带 `slTriggerPx` → `STOP_MARKET`(OCO 同时带 TP 也算,它确实有止损),只有 `tpTriggerPx` → `TAKE_PROFIT_MARKET`(**不许冒充止损**),side → `BUY`/`SELL`,stop_price 取对应的触发价,reduce_only 对带触发价的 conditional/oco 置 true(net 模式下它们就是平仓腿,OKX 对附带单不回 `reduceOnly`)—— 不翻译的话 `threads.ts` 的 `hasLiveStop()` 认不出来,巡检会一直判保护缺失并重复补挂;as_of=now。五次 CLI 调用可并发,**任何一次失败(含两种算法单查询)整份快照就失败** —— 把算法单错误吞成 `[]` 等于对巡检说「现在没有保护单」。张数换币需要 `ctVal`:**规格没拿到就报数据不可用,不做 1:1 回退** |
| symbolRules / symbols / markPrice | 走 §3 的行情模块(不用 CLI) | |
| placeEntry(req) | `swap place --instId --side buy/sell --ordType market/limit [--px] --sz <张> --tdMode cross --clOrdId <cid'>` | 市价单回执 `sCode==='0'` → 立刻 `swap get --clOrdId` 拿 `state/avgPx/accFillSz`:`filled`→outcome filled,否则 submitted;限价 → submitted |
| openWithProtection(req) | `swap place ... --ordType market --sz --clOrdId <cid'> --slTriggerPx <stop> --slOrdPx -1 --slTriggerPxType mark [--tpTriggerPx <tp> --tpOrdPx -1 --tpTriggerPxType mark]` | 附带止盈止损跟单一起提交(一次原子请求,比 Binance 的「先开仓再挂 STOP_MARKET」更安全)。下单回执不返回 algoId:成交后 `swap get --instId --clOrdId` 读**父订单详情**,从 `attachAlgoOrds[].attachAlgoId`(或 `linkedAlgoOrd.algoId`)取归属。CLI 的 `swap place` **不支持** `--attachAlgoClOrdId`(`buildAttachAlgoOrds` 只拼 tp/sl 价格字段),所以附带腿没有我们自己的客户端 id;父订单详情给不出 algoId 时腿的 outcome 就是 **`unknown`** —— **绝不按「最新的 reduceOnly 单 / 最新的一张」认领**(会认领别人的手工止损,后续还会撤掉它)。拿到后把 `stop_client_algo_id → algoId`、`tp client_algo_id → algoId` 写进 KV(`okx.algo.v1:<cid>`)。附带单不能拆开撤:stop 与 tp 附带在一起时是一张 OCO;runtime 的 stop/tp 分别 `AlgoLegReceipt` 都回同一个 algoId,`tp.outcome` 在没 tp 时 `skipped` |
| placeStop(symbol, position, stop_price, cid) | `swap algo place --instId --side <反向> --ordType conditional --sz <当前持仓张数> --reduceOnly --tdMode <仓位实际 mgnMode> --slTriggerPx <stop> --slOrdPx -1 --slTriggerPxType mark --cxlOnClosePos --clOrdId <cid'>` | OKX 没有 `closePosition=true` 的等价物:张数与 `tdMode` 都用当前持仓(`account positions --instId` 现查)。**独立挂的算法单可以带客户端 id**:CLI 的 `--clOrdId` 会透到 OKX 的 `algoClOrdId`,所以 `algoOrderExists`/`listAlgoOrders`/`cancelAlgoOrder` 有交易所侧的精确凭据,不必只靠 KV;KV 仍然记 cid→algoId(附带腿只有这条路) |
| placeTakeProfit | 同上,`--tpTriggerPx <tp> --tpOrdPx -1 --tpTriggerPxType mark` | |
| algoOrderExists(symbol, client_algo_id) | 先按 `algoClOrdId === cid'` 在 `swap algo orders`(conditional + oco)里找,没有再用 KV 的 algoId 比 | 两种证据都没有 → null(不确定,**不是「没挂」**);列表查询失败 → null |
| cancelAlgoOrder | `swap algo cancel --instId --algoId <id>` | |
| listAlgoOrders(symbol) | `swap algo orders --instId ...` 两种 ordType 合并;client_algo_id 从 KV 反查,查不到的用 `algoId` 当 client_algo_id | |
| closePosition(symbol, cid) | `swap close --instId --mgnMode cross --posSide net --autoCxl` | `autoCxl` 顺带撤掉该合约挂单;`--mgnMode` 取**该仓位实际的** `mgnMode`(现查 `account positions --instId`),不是实例字段。无持仓时 OKX 报 `51023`/`51169` → `closed: true`(已平,等价于 Binance -4509)。**`51024` 是「账户被限制」,不是「仓位不存在」,不在这个集合里**。写超时 / `50004` → `closed:false, ambiguous:true`,runtime 把意图留在 unknown 并按新鲜仓位收敛,不写 failed |
| reducePosition(symbol, qty, cid) | `swap place --ordType market --reduceOnly --sz <张> --clOrdId` | side 与持仓相反 |
| cancelAll(symbol) | `swap orders --instId`(open)逐张 `swap cancel <instId> --ordId` + `swap algo orders` 逐张 `swap algo cancel` | 用 `swap batch --action cancel` 可以合并普通单;算法单只能逐张 |
| cancelOrder(symbol, cid) | `swap cancel <instId> --clOrdId <cid'>`;失败再按 KV 当算法单撤 | OKX 51400/51401(不存在/已撤)→ ok:true |
| getOrder(symbol, cid, fresh) | `swap get --instId --clOrdId <cid'>` | state 映射:`live`→NEW,`partially_filled`→PARTIALLY_FILLED,`filled`→FILLED,`canceled`/`mmp_canceled`→CANCELED;`avgPx`,`accFillSz×ctVal`;`51603`(订单不存在)→ null;缓存 30s 按 cid |
| setLeverage(symbol, lev) | `swap leverage --instId --lever <n> --mgnMode <该 symbol 的模式>` | 记住 symbol→lever,给下面的重设用 |
| setMarginType(symbol, mode) | 不发请求:OKX 的 tdMode 是每张单指定,**按 symbol** 记(不是实例级字段)。runtime 的顺序是 setLeverage → setMarginType,而 OKX 的杠杆按 (instId, mgnMode) 存 —— 模式在这里变了就**在新模式下把杠杆重设一次**,等价于「先定模式再设杠杆」,且不动 Binance 的调用顺序 | 返回 ok |
| settlement(symbol, start, end, fresh) | `swap fills --instId --json`(近 3 天;>3 天 `--archive`)+ `account bills --instType SWAP --ccy USDT --json`(≤7 天;>7 天 `--archive`) | trades:`ts` 在窗内、`instId` 匹配;side=`side` 大写、price=`fillPx`、qty=`fillSz×ctVal`、realized_pnl=`fillPnl`、**commission=`-fee`(保号,十进制字符串运算)** —— OKX 的 `fee` 负数=扣费、正数=maker 返佣,内部算的是 `realized - commission + funding`,取绝对值会把返佣反向记成支出。funding = bills 里 `type==='8'`(资金费)且 `instId` 匹配、`ts` 在窗内的 `pnl`(或 `balChg`)**十进制**求和,按 `billId` 去重;fills 抓不到 → 返回 null;fills 正常但 bills 失败 → `funding: null`。**覆盖证明**:CLI 1.4.7 的 `swap fills` 只透传 `instId/ordId/archive`(没有 begin/end/after/limit),`account bills` 只透传 `instType/ccy/limit`,两边都只拿得到最新一页 —— 整页塞满(fills 100、`--archive` 20、bills `--limit 100`)且最旧一条仍晚于窗口起点 = 起点之前的记录被挤掉了:fills 不完整 → **整个 settlement 返回 null**(调用方按「没查到」,绝不当成 0),bills 不完整 → `funding: null` |
| protectionCapability() | `'verified'` **在真实模拟盘上跑过 §7 的验证脚本之后**才切成 verified;实现里先读 KV `okx.protection.verified`,没有就 `'unverified'` | 与主仓「未验证通道不许新开仓」的规则一致 |
| netCheck(n) | `market ticker BTC-USDT-SWAP` n 次(公共)+ 1 次 `account balance`(签名) | |
| tick() | 返回 `[]` | |
| accountStalenessMs | 15s 缓存 + 15s CLI 超时 | account() 结果缓存 15s,写操作后 `invalidateAccount()` |

**clOrdId 规则**:OKX 只允许字母数字、≤32 位。内部 CID 形如 `tg-<hash>-e-0`。映射
`cid' = cid.replace(/[^A-Za-z0-9]/g, '')`,超长截到 32;需要可逆时**不**反解,而是 getOrder/cancelOrder
时用同一函数正向算出 cid' 去查。单元测试要覆盖:两个不同内部 CID 不能映射到同一个 cid'(在现有
CID 生成器的字符集内证明去掉连字符不会撞)。

**错误分类**:CLI 退出码 1 + 能解析出 `{sCode,sMsg}` 或 `{code,msg}` → `rejected`(带 code);
spawn 失败/超时/非 JSON → `transport`;OKX code 映射:`51008`(余额不足)、`51000`(参数错)等 rejected;
`50111`/`50113`(key 无效/权限)→ 带「请 `okx config init`」提示。

## 点击接入 API（2026-09-20）

以下控制面端点沿用 gateway 的本机访问与 Origin 检查。配置/安装不自动切换执行通道，不发订单。

| 方法与路径 | 请求 JSON | 响应 JSON |
|---|---|---|
| `POST /api/execution/okx/setup` | `{api_key, secret_key, passphrase, demo?:true, site?:"global", name?:"okx-demo"}` | `{ok, profile, demo, credentials_ok, error?, okx}` |
| `POST /api/execution/okx/install` | 无 | `{ok, cli, version, log_tail}` |
| `GET /api/wallet?refresh=1` | 无；refresh 可省略 | `{installed, cli, logged_in, email, login_type, account_name, account_id, checked_at}` |
| `POST /api/wallet/login` | 无 | `{url, session_id}` |
| `POST /api/wallet/login/poll` | `{session_id}` | 钱包状态，同 GET；poll 最多 90 秒，超时也刷新状态，可用同一 id 继续轮询 |
| `POST /api/wallet/logout` | 无 | 刷新后的钱包状态 |
| `GET /api/execution/okx/mcp` | 无 | `{cli_available, mcp_command, registered_in_claude, checked_at}` |
| `POST /api/execution/okx/mcp/register` | 无 | 刷新后的 MCP 状态 |

`demo` 默认 true，false 时默认名称 `okx-live`；`site` 支持 global/eea/us/tr。三项凭证必须为非空字符串。`ok` 表示配置保存成功，`credentials_ok` 是独立的只读余额检查结果；配置成功但凭证或网络检查失败时 `ok:true, credentials_ok:false`。安装超时 5 分钟，继承代理环境，日志末尾最多 4000 字符。钱包状态缓存 30 秒，三盏灯的 wallet 复用同一状态源。未获取到的账户字段为 null，时间均为 unix 毫秒。

**不存密钥边界**：本 fork 配置向导允许 gateway 单次接收 HTTP 凭证并直接作为 argv 透传到 `okx config add-profile AK=… SK=… PP=… demo=… site=… name=… --force`。gateway 不记录、不落库、不回显凭证，配置和检查失败只返回固定错误，不转发 CLI 原始输出；凭证只由官方 CLI 存入 `~/.okx/config.toml`。gateway 不打开该文件。该向导是原有「执行路径只传 profile」边界的明确例外；请求体与子进程 argv 不得接入日志采集。

保存后清空 availability 缓存并重读掩码版 `okx config show`；CLI 自动设置 default_profile。未设置 `TG_OKX_PROFILE` 时，后续后端创建使用新默认值，无需重启；显式环境变量仍优先。已运行的后端保持所绑定账户，避免在持仓期间自动切换账户；需要通过现有执行通道切换流程重建。

MCP 命令依据 CLI 1.4.7 的 `runSetup` 源码为独立 `okx-trade-mcp --modules all`，不是 `okx mcp`。注册调用 `claude mcp add --scope user --transport stdio okx-trade-mcp -- okx-trade-mcp --modules all`（存在本机 `~/.local/bin/okx-trade-mcp` 时使用绝对路径）；检测 `~/.claude.json` 的顶层 mcpServers。MCP 包独立于 trade CLI，`cli_available` 指 MCP 二进制；仅安装 trade CLI 不意味着 MCP 已安装。

公共 OKX REST 使用 Node 24 的 `http.setGlobalProxyFromEnv`（内部为 EnvHttpProxyAgent），支持 HTTP_PROXY/HTTPS_PROXY、ALL_PROXY 回退及对应小写变量，合并 NO_PROXY/no_proxy 并追加回环地址。它设置进程级 fetch dispatcher 和 http(s) Agent，因而同进程其他网络请求也遵循代理；行情的 HTTP/业务错误与重试行为保持原定义。无需新增 npm 依赖。
