# 盯盘 / 筛选 / 复盘 / Agent 重设计 + 组件接入标准(2026-09-24,另一工作线)

Jacky 要求：盯盘参数和筛选用起来顺手，资产以 OKX 为主;复盘、Agent 页对齐最新后端;各板块要串起来，并且有一个标准，让新组件、甚至用户自建的组件也能接进来。

## 一、调查结论(问题根因)

- **筛选页显示「币安上没有」不是文案问题，是数据源错了。**`funnel.ts` 的 `listTradableSymbols` / `fetchTickerMap` / `fetchNextFundingMap` 写死调用 `fapi.binance.com`,`TG_EXCHANGE=okx` 不生效。存在性判断、24h 成交额、资金费全部来自币安。`market-okx.ts` 里已有 OKX 封装，一个都没接上。
- **加币要手输。**`watch.tsx` 的加币框是纯文本框，校验不过就整批拒绝。同仓库 `workflow-form.tsx` 的 `WatchlistEditor` 已经做了输入即联想，但两页没共用。另外 Agent 页里的「盯盘参数」抽屉和独立的盯盘页是两套实现，功能重叠。
- **没有每天全市场扫描。**雷达按 12h / 3d / 7d 定时跑，默认只扫「观察列表 ∪ 白名单」;只有切到 top_volume 模式才扫成交额前 N,而且这个排名也来自币安。研究侧已有 OKX 口径的资产池(现货在售 + 90 天成交额 + 排除稳定币),但只是离线脚本，前端拿不到。
- **复盘页没接上新后端。**判断账本 jl-v2 的 trigger / prompt_version / holding_reason 分层、regret_hold 与 regret_exit 的拆分，后端都已产出，前端类型没声明、页面也没渲染。影子候选的结算、判断回放的账户折算，复盘页都没引用。
- **Agent 页的对话工具很旧。**它用的是 25 个硬编码工具，里面没有判断账本、研究、策略、候选、进化;深链也只能跳交易、楼层、信息员、设置、日志。
- **各板块靠 runtime.ts 里手写的函数调用串起来，不是协议。**
  - 事件总线大多只推给前端，后端没有消费者;交接表只是日志。
  - 9 个角色里有 4 个是 enabled=false 的占位。
  - 唯一协议化的一环是研究侧的 `compile-binding`:策略 IR 按六角色切片，每条规则标 code 或 model。它在研究侧已通，到实盘这一段还没接。

## 二、重设计

### 1. OKX 资产全集(后端)

- 新增 `universe-okx.ts`,常驻网关。每天 UTC 00:10 自动刷新一次，也可以手动刷新。内容是 OKX 全部 USDT 现货和永续在售清单，附 24h 成交额、90 天成交额排名、是否有永续、最新价、24h 涨跌、资金费(永续);稳定币、包装币打标排除。结果落库，接口读缓存，不要每次请求都打 OKX。
- `GET /api/universe?market=spot|perp|all&q=&limit=`:返回排序后的资产列表和刷新时间，给联想和选择器用。
- `POST /api/universe/refresh`:手动刷新。
- **每天全市场代码扫描**:刷新之后，零模型地对全集跑一遍筛选指标(沿用 funnel 的指标口径),存成当天的「全市场扫描」;雷达的候选从这里挑，用户的收藏(观察列表)是它的子集。
- `funnel.ts` 按 `TG_EXCHANGE` 分流:OKX 时，存在性、成交额、资金费都走 OKX,文案改成「OKX 上没有」;币安分支保持原样。

### 2. 盯盘参数页(前端)

- 合成一个页面、一个组件：独立盯盘页和 Agent 页的抽屉共用它。
- **资产选择器**:搜索框即时联想(代码 / 名称);下面列 OKX 资产，可按现货/永续筛，按成交额、涨跌、资金费排序，每行一个「+」一键加入，也可以勾选后批量加入。已在观察列表的显示「已监控」。
- **观察列表**:卡片或行，每个币显示最新价、24h、是否在雷达当天候选里;可一键移除，可拖动排序;上限显示「32 / 60」。
- **节奏参数**分组，用人话写：多久看一次(周期)、怎么扫(扫描方式)、心跳频率;每项都有一句解释和推荐值。
- 顶部一句话说明这些参数影响什么，例如「影响每天判断次数与花费」。

### 3. 筛选页(前端)

- 顶部固定显示「今天的全市场扫描:扫了 N 个 OKX 资产，挑出 M 个候选，时间 xx」。
- 候选表：代码、市场、分数、入选理由(人话)、成交额、资金费、是否已监控;一键加入观察列表。
- 历史扫描折叠起来;设置(白名单、扫描模式)收进抽屉。
- 所有「币安」相关文字和数据源都改成 OKX。

### 4. 复盘页(前端 + 少量类型)

- 分成三块:「这笔赚没赚」(交易与账户，现有 history)、「这类判断值不值」(判断账本 jl-v2,可在 策略 / 触发 / prompt 版本 之间切换分层，regret 拆成该走没走、不该走走了)、「候选和策略」(影子候选结算、链接到「我的策略」对应的策略对象)。
- 统计口径都写明样本量;笔数 < 30 标「观察」;平均值旁给中位数和截尾均值(复用 centerStats 的口径)。
- 类型放新文件 `api/ledger-v2.ts`,不改别人正在动的 `api/types.ts`。

### 5. Agent 页

- 对话工具补上：判断账本摘要、影子候选列表、我的策略 / 回测报告只读、进化方格摘要、全市场扫描结果;全部只读。
- 回答里带深链：研究工作台、我的策略、判断记录、信号市场、进化页。
- 右栏「团队」改成各角色的状态和 30 天方格(复用进化组件),点进去就是对应页面。
- 盯盘参数抽屉复用新的盯盘组件。

## 三、组件接入标准(草案 v0)

一个组件，不管是内置角色、策略、信号源、过滤器、风控规则，还是用户自建的，都要声明一份 `ComponentManifest`:

1. `id`、`kind`(deterministic / llm_recipe / llm_session)、`role`(接在哪个角色位：雷达 / 判断 / 几何 / 风控 / 持仓 / 执行 / 复盘 / 研究)。
2. **输入**:订阅哪些事件(必须在事件白名单里)、读哪些数据(只读切片)。
3. **输出**:产生哪些事件或建议，每种都要有 JSON Schema(contracts 是唯一真源)。
4. **权限三档**:只读 / 提议(只到 intent.propose)/ 写钱(只有 executor)。用户自建组件最高只能到「提议」。风控类组件只能否决或收紧。以上在注册时校验，不靠约定。
5. **每条规则标 code 或 model**:沿用 compile-binding 的做法，不允许笼统写「模型负责」。
6. **不能表达的就拒绝**:沿用 compilerGaps 的 block / warn 分级，不静默近似、不编数。
7. **健康状态**:最近一次运行、成功或失败、失败原因，统一出现在 `/api/bots` 和楼层。
8. **进化指标**:声明一个每日结算函数，接入 `/api/evolution`,自动在进化页得到一行方格。
9. **UI 卡片**:声明 title、状态、主指标，楼层和 Agent 右栏用通用卡片渲染，不再每个板块自己画。
10. **单一注册表**:所有组件经 registry 注册，不允许绕过注册直接改 runtime.ts。

**用户自建组件的最短路径**(按能力由小到大):
- 研究原语(`define()`,纯函数)→ 研究和回测可用;
- 策略(IR → binding)→ 经部署页签和人工确认进实盘;
- 外部信号源(信号市场订阅)→ 只作为判断的证据。

Pine 脚本目前只能停在研究和回测，不能进实盘。

**落地顺序**:
1. 先把 binding 六角色切片接到实盘(apply),这是现成的一半协议;
2. 给 BotProfile 加 manifest 字段(权限、输入输出、进化指标);
3. 4 个占位角色补健康状态和卡片;
4. 最后才抽统一 registry,过早抽象会重复「六个角色各画一套」的错误。

本轮先做第二节的 1–5,并把第三节写进 `v3-ui-contract` 作为草案;标准的代码落地单独排期。
