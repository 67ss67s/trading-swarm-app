## 1. 它在 gate 里是什么位置

Notebook §1 第 7 条「三层监督:状态提示 → 侧栏预览 → 需要处理时进入完整工作台」。
现在的 webui 只有第三层(交易/Agent/信息员/判断记录/记忆/复盘/回放/策略库/日志/设置 都是工作台)。
Ops Floor 补前两层:

| 层 | 楼层里的位置 | 点进去到哪 |
|---|---|---|
| 状态提示 | 每个桌子上的像素人 + presence(idle/thinking/working/waiting/blocked/done/offline)+ 一句当前动作 | — |
| 侧栏预览 | 右栏 Agent Council(8 角色 + AI/CODE/EXEC 徽章)、Live Handoffs 流、左栏 Mission Source / 收件箱 | 点角色 → 底部「选中 agent」卡 |
| 完整工作台 | 每个桌子都是既有页面的入口 | radar→`#/intel`(筛选页出来后→`#/screener`);thread_manager→`#/judgments`;executor→`#/agent` 执行卡;reviewer→`#/history`+`#/memory`;strategy_lab→`#/strategies`/`#/replay`;risk_sentinel→`#/settings` 风控;gate_captain→`#/agent` 对话 |

所以 **楼层不替代任何页,也不新增任何权限**。它是 overview 的可视化版本。
Agent 页的对话框就是 Gate Captain 的桌子;楼层上的「共同交接桌」是 bot_handoffs 的可视化。

## 3. Presence 怎么来(已与并行 session 对齐 09-05 23:40:网关代码派生,不落库,模型不能写)

`GET /api/bots` 返回 `{ bots: BotProfile[], runs: BotRun[], handoffs: BotHandoff[] }`,每个 BotProfile 带
`presence: { state: 'idle'|'thinking'|'working'|'waiting'|'blocked'|'done'|'off', action: string|null, since: number|null, next_at: number|null }`,
由 runtime 从运行时状态推导(radar=筛选进行中 working;thread_manager=inFlight episode thinking / 队列等待 waiting;executor=连接 ok idle / error blocked / 有未回执订单 working;risk_sentinel=halted blocked;gate_captain=有 pending handoff waiting;enabled=false 一律 off)。
下表是**前端兜底**:网关还没返回 presence 时用 overview/execution 推,返回后兜底让位。

| 角色 | working | waiting | blocked | idle | offline |
|---|---|---|---|---|---|
| thread_manager | queue.running.kind ∈ scan/review(带 step 文案) | queue.pending>0 | 最近 activity brain_error(5 分钟内) | 其余 | — |
| radar | queue.running.kind=info 或 screener 最新 run=running | — | — | 其余(显示下次筛选倒计时) | — |
| executor | 有线程处于 entry 挂单/保护腿挂单中 | — | halted 或任一线程 attention | 其余 | execution.connection 未就绪 |
| gate_captain | chat 正在生成(chat.message role=assistant 且 pending) | 收件箱非空 | — | 其余 | — |
| risk_sentinel(CODE) | — | 日亏接近上限(≥70%) | halted | 其余(「盯盘中」) | — |
| strategy_lab | backtest.running 非空 | — | — | — | profile.enabled=false 时灰 |
| reviewer / portfolio_manager | — | — | — | — | 灰(占位,tooltip 显示 note「还差什么」) |

**诚实原则**:`enabled=false` 的角色画成灰色并显示 note,不假装在工作;deterministic 角色
(risk_sentinel、executor)用 CODE/EXEC 徽章,和 LLM 角色视觉区分——有头像不等于能自由调工具(notebook §3)。

分工:gateway 全部(routes-bots/routes-screener/radar.ts/runtime/presence)+ nav/App/client/types 的追加由并行 session(jacky-2f)负责;本页只新增 `pages/floor.tsx` + `components/floor/*`,四处接线等对方 ping 后再加。

## 5. 视觉

- 楼层区强制深色(和参考物一致),外壳仍跟随主题;像素人用 12×12 位图(CSS box-shadow),8 个角色 8 种色,
  颜色同时用于右栏 tile 和 feed 的箭头,保持「颜色 = 角色」。
- 动效只动 transform(项目约定):working 呼吸、handoff 时一个小包裹从 from 桌子飞到 to 桌子(可 reduce-motion 关)。
- 桌上小屏显示该角色最近一条动作(≤ 40 字)。

## 7. 待并行 session / Codex 确认的问题

1. `/api/bots/handoffs` 是否返回 `payload`(watchlist 提案)——收件箱要能「应用」,否则只做跳转到筛选页。
2. Gate Captain 的「chat 正在生成」目前只能从 chat.message 事件推断;要不要 `queue.running.kind='chat'`。
3. 楼层要不要成为默认首页(`#/floor` 取代 `#/trade` 作为落地页)。我的建议:不,交易页仍是首页,楼层排第二。

## 8. Codex 对抗评审(gpt-6-astra,`.codex-reports/ops-floor-review.md`)与处置

采纳并已改:
- **映射行 ≠ 交接**:activity 映射行标「系统事件」徽章,真 bot_handoffs 行标「交接」并带 handoff_id;飞包动画只给真交接;底栏「HANDOFFS 24H」只数真交接。
- **时序/归属**:`rejected` 回给 thread_manager 不送 executor;`thread_opened` 改为 executor → thread_manager 的回执「已挂单」;`chat_action` 降亮。
- **presence 口径**:halted 时 risk_sentinel 是「生效中(working)」不是故障;executor 挂单等成交是 waiting 不是 working;`enabled=false` 文案改「未完整接线」。
- **楼层只读**:交接流里的 watchlist 提案只**预览 diff**,应用去筛选页确认;楼层唯一的写动作是 ack(= 已阅,不代表接手或授权)。
- **首屏回答「现在最需要我处理什么」**:收件箱列前 3 件(内容 / 等了多久 / 责任人 / 去处理)。
- **底栏**:去掉全局 confidence(改为「最新判断 + 自报信心」);paused 不冒充观察模式,改为 APPROVAL MODE(auto-approve / human gate)。
